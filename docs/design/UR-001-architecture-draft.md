# UR-001 — Архитектура v0 (черновик)

Статус: черновик по обсуждению с владельцем 2026-09-18. Не принят. Проект — Epochnotes.

## 0. Задача
Solana меняет сеть, клиенты и библиотеки волнами (август–октябрь 2026: транзакции v1, снижение rent SIMD-0437, слот 300 мс → 250/200, Alpenglow 28.09, breaking changes solana-sdk). Экосистема ломается тихо, каждый проект чинит у себя; общего инструмента нет (`research/LIVE_PROBLEMS_2026-09-18.md`). Инструмент говорит разработчику: что у тебя сломается, где, как чинить — и отслеживает деньги, которые изменения высвобождают (излишек rent).

## 1. Слои
```
источники (SIMD, релизы Agave/клиентов, solana.com/upgrades, GitHub issues, feature gates в сети)
   │  пайплайн сбора: Claude готовит черновик записи со ссылками → человек проверяет
   ▼
ХАБ: подписанный реестр изменений (записи + журнал версий + издатели)
   ▼
движок проверок (одна библиотека TypeScript)
   ├─ знания / скилл   ├─ rent   ├─ проверка репозитория   ├─ (дальше: слоты, Alpenglow, …)
   ▼
оболочки: CLI · GitHub Action · скилл для Claude · веб-страница
```
Программа Solana: реестр издателей и журнал версий реестра.

## 2. Запись реестра
Одна запись = одно изменение на одной оси. Подписываются только устойчивые факты.
| Поле | Смысл |
|---|---|
| `id`, `rev` | стабильный идентификатор; правка = новая редакция |
| `axis` | `protocol` / `client` / `library` |
| `subject` | например SIMD-0385; Agave 4.3; `@solana/kit` |
| `applies` | для protocol — адрес feature gate; для client/library — диапазоны версий (semver) |
| `relations` | `requires`, `supersedes`, `related` → ссылки на другие записи (граф) |
| `breaks` | что ломается: поверхности (RPC-вызов, декодер, программа, стрим) |
| `detect` | правила обнаружения: поиск в коде, версии в lock-файлах, проверки в работе; у каждого — уровень уверенности |
| `fix` | как чинить: текст, патч/шаблон, ссылки |
| `sources` | URL первичных источников с датой |
**Статус активации в записи не хранится** — движок читает его из аккаунта feature gate на нужном кластере в момент проверки.

## 3. Версии
- **Журнал версий реестра** у каждого издателя линейный и только дописывается: версия = Merkle-корень всех записей + `prev_root`. Что угодно поменялось — новая версия; изменения за день публикуются одной версией.
- **Изменения Agave, протокола, библиотек — записи**, а не версии реестра. Одновременный выход Agave и изменение протокола = две записи с отношением `requires`, в одной или двух публикациях — смысл не меняется, применимость считается по условиям.
- **Параллельность — между издателями:** у Anza, у нас, у Helius свои журналы. Клиент берёт последние версии журналов доверенных издателей, объединяет записи по `id`, конфликт решает приоритет издателя у пользователя и показывается явно.
- Пример: в один день Agave 4.3 и активация Alpenglow → Anza публикует «Agave 4.3» и «Alpenglow: что ломается» (`requires`); мы публикуем правило для индексаторов со ссылкой на запись Anza; статус «активировано» никто не публикует — его видно в сети.

## 4. Подпись и программа
- Лист = sha256 канонической сериализации записи; версия = Merkle-корень.
- `Publisher` PDA: ключ, имя, статус, кем допущен. `RegistryVersion` PDA: номер, `merkle_root`, `prev_root`, URI содержимого, слот, подписант.
- Инструкции: `register_publisher`, `publish_version`, `revoke_entry`.
- Клиент проверяет: запись входит в версию N (Merkle-доказательство); версия подписана допущенным издателем; цепочка `prev_root` не разорвана.
- **Сначала единственный издатель — мы.** SF/Anza как издатели — рост, не условие запуска (согласие не проверено).

## 5. Место VRE
- **Переиспользуем снапшоты VRE:** Merkle-дерево и доказательства (`sdk/snapshot.ts`: `buildMerkleRoot`, `buildMerkleProof`, `verifySnapshotMerkleProof`), чтение по URI и хеш-адресуемым зеркалам (`snapshot_source.ts`), проверка без доверия серверу, квитанция Irys. Реестр = снапшот записей.
- Проверяемая случайность — позже: случайный выбор рецензентов записи из пула издателей; случайная выборка репозиториев/аккаунтов для выборочной проверки правил.

## 6. Модули
- **Знания / скилл** — первый потребитель реестра (не отдельная база): отвечает «что изменилось и что мне делать» для ИИ-ассистентов разработчика.
- **Rent** — сканер излишка (кошелёк и программа, публичные данные) + возврат: адаптеры закрытия под 2–3 протокола для пользователей, генератор `withdraw_excess` для разработчиков. Замер: `research/spikes/rent-stuck-2026-09-18/README.md`.
- **Проверка репозитория** — правила из реестра: поиск в коде (`maxSupportedTransactionVersion: 0` и т.п.), версии в lock-файлах, прогон декодера/RPC/стрима через эталонные v1-транзакции; уровни уверенности «точно сломается / проверьте / скорее норм» (пример VRE: слоты SlotHashes по дизайну vs таймеры в слотах).
- **Слой издателя** — схема + валидатор + предпросмотр «что найдёт правило» + прогон на оценочном корпусе до публикации; PR с YAML и команда CLI, веб-редактор позже.
