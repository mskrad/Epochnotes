# UR-001 — Формат записи реестра (v1)

Статус: проектное решение задачи UR-001, 2026-09-18. Дополняет принятую архитектуру (`UR-001-architecture-draft.md` §2–§4).
Артефакты: схема `UR-001-entry.schema.json` (JSON Schema 2020-12), эталонная запись `UR-001-example-tx-v1.yaml`.
Реализация (zod, каноникализация, валидатор в CLI) — задача UR-003; схема из кода должна остаться эквивалентной этой.

## 1. Принципы
1. **Одна запись = одно изменение на одной оси** (`protocol` / `client` / `library`).
2. **Подписываются только устойчивые факты.** Статус активации, слот активации, «сейчас сломано/починено» в запись не попадают — схема закрыта (`additionalProperties: false`), такие поля отклоняются.
3. **Каждое утверждение прослеживается до источника:** `breaks[].evidence` — индексы в `sources[]`. Источник без даты получения не принимается.
4. **Правила обнаружения живут в записи, не в движке:** новая поломка = новая редакция записи, а не релиз инструмента.
5. Тексты записей — на английском (реестр читают разработчики экосистемы и ИИ-ассистенты); проектная документация — на русском.

## 2. Поля
| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `schema_version` | `1` | да | версия формата; смена формата = новое число, старые записи остаются проверяемыми |
| `id` | slug | да | стабильный идентификатор (`tx-v1`); не меняется при правках |
| `rev` | int ≥ 1 | да | редакция; любая правка содержимого = `rev + 1` |
| `axis` | enum | да | `protocol` / `client` / `library` |
| `subject` | объект | да | `type` (`simd` / `client-release` / `package`), `name` (`SIMD-0385`), `title` |
| `applies` | объект | да | `gates[]` (адрес feature gate, метка, эффект) и/или `versions[]` (экосистема, пакет, диапазон semver); непустой |
| `relations` | массив | нет | `requires` / `supersedes` / `related` → `id` другой записи |
| `breaks` | массив ≥ 1 | да | `surface` (`rpc`, `decoder`, `stream`, `program`, `sdk`, `wallet`, `economics`), `summary`, `evidence[]` |
| `detect` | массив | нет | правило: `rule`, `kind`, `confidence`, `summary` + параметры вида |
| `fix` | массив ≥ 1 | да | `summary`, `detail`, `for_rules[]`, `links[]` |
| `sources` | массив ≥ 1 | да | `kind`, `ref`, `retrieved` (дата), `note` |

**`applies.gates` — список, а не один адрес.** Проверено по коду agave: у SIMD-0437 пять gate (по одному на шаг ставки), у SIMD-0525 — четыре (350/300/250/200 мс). Один gate на изменение — частный случай.

**Виды правил `detect.kind`:**
- `code-pattern` — `pattern` (регулярное выражение) + `languages`;
- `lockfile-version` — `package` {`ecosystem`, `name`, `range`};
- `runtime-probe` — `probe` {`method`, `fixture`, `expect`}: прогон читателя проекта на известной транзакции/аккаунте.

**Уровни `confidence`:** `breaks` — точно сломается; `check` — проверьте; `likely-ok` — скорее норм (архитектура §6).

## 3. Статус активации (вне записи)
Движок читает аккаунт каждого gate из `applies.gates` на выбранном кластере в момент проверки. Три состояния, а не два:
| Состояние | Признак в сети |
|---|---|
| `absent` | аккаунта gate нет — активация не запланирована |
| `pending` | аккаунт есть (владелец `Feature111…`), `activated_at = None` — ждёт границы эпохи |
| `active{slot}` | `activated_at = Some(slot)` |
Отчёт всегда называет кластер и слот запроса. Для записи с несколькими gate статус — по каждому gate («шаг 2 из 5 активен»).

## 4. Каноническая форма и хеш листа
1. YAML (источник, для людей) → модель данных JSON. Разрешены: объект, массив, строка, целое, булево. **Float и `null` запрещены** (схемой и валидатором), даты — строки `YYYY-MM-DD`.
2. Значения по умолчанию подставляются **до** каноникализации (`relations: []`, `detect: []`), чтобы «поля нет» и «поле пусто» давали один хеш.
3. Строки нормализуются в Unicode NFC.
4. Сериализация — JCS (RFC 8785): ключи отсортированы, без пробелов, UTF-8. При запрете float JCS сводится к сортировке ключей + компактному JSON, поэтому реализация проверяема независимо на любом языке.
5. **Лист = sha256(JCS-байты)**. Порядок ключей на входе на хеш не влияет; порядок элементов массивов — влияет (это авторский порядок).
6. Разделение доменов «лист/узел» в Merkle-дереве решается в UR-005 после чтения схемы пар VRE (`sha256_pair_v1`).

## 5. Семантические проверки валидатора (сверх схемы)
- индексы `breaks[].evidence` существуют в `sources[]`; `fix[].for_rules` ссылаются на существующие `detect[].rule`;
- `relations[].id` существуют в реестре; циклов по `requires` и `supersedes` нет;
- `rule` уникален в пределах записи; `id` уникален в реестре; `rev` новой редакции = предыдущая + 1;
- `pattern` компилируется; `range` — корректный semver-диапазон; `address` декодируется в 32 байта base58.
