01 / From source to understanding

How it works

Signed entries

Each change is an entry built from primary sources — a SIMD or an EIP, the client's code, the chain itself. A version of the registry is a Merkle root, signed by its publisher and anchored by a program on Solana devnet.

Checks

check repo finds the code a change breaks; check rpc asks a provider, read-only, whether it behaves as the entry says; status reads the activation from each chain at the moment you ask.

Watcher

Every day it reads the feature gates agave declares and their state on three Solana clusters, and drafts an entry for what moved outside the registry. A person finishes the draft from the SIMD and signs it.

Alpenglow

SIMD-0326Solanaentry alpenglow · rev 1

What breaks

  • stream Votes stop being transactions on chain: validators send them directly to each other. Initially a validator admission ticket reproduces the incentives of today's vote transaction fees. Voting is not invisible afterwards: for rewards, the leader of slot s+8 can post up to two vote aggregates for slot s. Code that reads individual vote transactions out of blocks no longer finds them.
  • rpc Optimistic confirmation is superseded by faster actual finality; the SIMD names this as the most visible change.

How to fix it

  • Do not derive validator activity from vote transactions in blocks, and review code that relies on optimistic confirmation as something distinct from finality.

Set Code for EOAs

EIP-7702EthereumBaseentry eip-7702 · rev 1 · 3 static rule(s), 2 RPC probe(s)

What breaks

  • program EIP-7702 breaks the invariant that msg.sender == tx.origin holds only in the top frame of a transaction: a delegated account can make several calls in one transaction. Reentrancy guards of the style require(tx.origin == msg.sender) and atomic sandwich protections that rely on tx.origin no longer hold. Using that check only to know that the sender is an EOA is, by the EIP's own reading, not affected.
  • program An account delegated under EIP-7702 has code: the delegation indicator, 0xef0100 followed by the address of the delegate, and EXTCODESIZE returns 23 for it. A check that reads code as "a contract" or no code as "an EOA" — an isContract call, a test of code.length or extcodesize — now takes a delegated EOA for a contract.
  • program OpenZeppelin's SignatureChecker.isValidSignatureNow checks an ECDSA signature only when the signer has no code, and otherwise asks the signer for ERC-1271. A delegated EOA has code, so its ECDSA signature is not checked as such: it is valid only if the delegate implements ERC-1271 and accepts it.
  • wallet OpenZeppelin's ERC721Utils.checkOnERC721Received calls onERC721Received on any recipient with code, and reverts when the call fails or returns another value. A safe transfer or a safe mint to a delegated EOA reverts unless its delegate implements the receiver.
  • sdk eth_getCode of a delegated EOA returns the 23-byte delegation indicator, and the account still sends transactions. Telling contracts from EOAs by whether eth_getCode is empty no longer works.

How to fix it

  • Replace a reentrancy guard built on tx.origin == msg.sender with one held in a transient storage variable, as the EIP suggests. A sandwich protection built on tx.origin has no replacement in the EIP, which calls relying on it a bad practice: it has to be designed again, not patched.
  • Where it matters whether an account is a delegated EOA, read the first three bytes of its code: 0xef0100 marks the delegation indicator (OpenZeppelin's EIP7702Utils.fetchDelegate returns the delegate), and decide explicitly how such an account is treated — for a signature, ECDSA, ERC-1271, or both.
  • A contract meant to be a delegate implements the receiver hooks the accounts that delegate to it rely on, such as onERC721Received: OpenZeppelin's ERC721Utils calls it on every recipient with code.

Incrementally Reduce lamports_per_byte to 696

SIMD-0437Solanaentry rent-simd-0437 · rev 1

What breaks

  • economics The minimum balance of an account is (128 + data size in bytes) * lamports_per_byte, and every step lowers lamports_per_byte. An account funded at an earlier, higher minimum keeps the difference: the SIMD allows reducing the balance to the new minimum, it does not return anything by itself.
  • sdk A lamports_per_byte value compiled into a client or program goes stale at every step: on activation the value changes in the bank and in the Rent sysvar, while DEFAULT_LAMPORTS_PER_BYTE in the SDKs is updated only after activation. The SIMD calls the reduction strictly a relaxation: existing program logic keeps working, so a stale higher constant overpays rather than fails.
  • program The reduction is not guaranteed to be one-way. The SIMD states that rent can be increased back to the legacy value in case of excessive state growth, noting that SIMD-0392 allows this without significant disruption to existing accounts; agave already declares a gate set_lamports_per_byte_to_6960, registered as "SIMD-0438: Reset lamports per byte to legacy value of 6960". A minimum balance fixed at a reduced value can therefore become too low for newly created accounts.

How to fix it

  • Take the minimum balance from the cluster at run time (the Rent sysvar in programs, getMinimumBalanceForRentExemption in clients) instead of a compiled-in lamports_per_byte.

Reduce Slot Times

SIMD-0525Solanaentry slot-duration · rev 1

What breaks

  • program A duration expressed in slots shrinks in wall-clock time with every stage: the SIMD tells dapp developers and off-chain services to stop assuming that 400 ms * slots is a stable conversion. A timer of N slots lasts half as long at 200 ms as it did at 400 ms.
  • sdk SDK constants stay at their 400 ms values at first: static constants for default slot duration, ticks per second, slots per year and slot-to-time conversion may keep describing 400 ms while the cluster runs 350, 300, 250 or 200 ms banks.
  • economics Per-slot limits scale down in proportion to the slot time so that the wall-clock rate stays approximately the same. From the 400 ms baseline of 60,000,000 the maximum block compute units become 37,500,000 at 250 ms and 30,000,000 at 200 ms; the maximum writable-account compute units go from 24,000,000 to 15,000,000 and 12,000,000. The ratios apply to whatever baseline is active: with the 100,000,000 block limit of SIMD-0286 the values are 62,500,000 and 50,000,000. Code tuned to the per-block or per-account limit of a 400 ms slot exceeds the scaled one.
  • program An epoch stays 432,000 slots, so it lasts half as long at 200 ms as at 400 ms. Anything scheduled per epoch happens twice as often in wall-clock time.

How to fix it

  • Keep slot counts only where slot semantics are intended; where a duration means wall-clock time, do not derive it from a fixed milliseconds-per-slot constant. The SIMD advises preferring cluster-provided timing parameters once they are available.

Transaction V1 Format

SIMD-0385Solanaentry tx-v1 · rev 1 · 9 static rule(s), 1 RPC probe(s)

What breaks

  • rpc getTransaction, and getBlock with transactionDetails full or accounts, fail with JSON-RPC error -32015 "Transaction version (1) is not supported by the requesting client" when the request omits maxSupportedTransactionVersion or sets it to 0 and the result contains a version 1 transaction. getBlock with transactionDetails signatures or none is not affected.
  • decoder A serialized version 1 transaction starts with the version byte 129 (0x81). A decoder written for the legacy and version 0 layouts has no branch for that value.
  • sdk @solana/kit 8.0.0 removed three compute-unit-limit helpers from @solana/kit in favour of resource-limit helpers that also set the loaded accounts data size limit for version 1 transactions, and removed the fixed transaction size constants from @solana/transactions because version 1 transactions have a larger size limit.
  • decoder The maximum size of a version 1 transaction is 4096 bytes; the prior maximum was 1232. A buffer or a size check fixed at 1232 bytes is too small for a valid version 1 transaction.
  • sdk @solana/web3.js 1.98.4 cannot read a version 1 transaction even when maxSupportedTransactionVersion is 1: getTransaction and getParsedTransaction throw a StructError on the version field, and getBlock fails the same way. 1.99.0 reads all three and returns a MessageV1.

How to fix it

  • Pass maxSupportedTransactionVersion 1 in getTransaction and getBlock; with @solana/web3.js this also needs version 1.99.0 or later.
  • When moving to @solana/kit 8.0.0 or later, replace the compute-unit-limit helpers with the resource-limit helpers named in the release notes.
  • Set the maximum supported transaction version to 1 in the configuration of the RPC client (Some(1) in Rust, rpc.MaxSupportedTransactionVersion1 or uint64(1) in Go, max_supported_transaction_version=1 in Python), and check that the client library in use can decode a version 1 transaction.

04 / Put the record to work

Check it yourself

Install the CLI with npm install -g @epochnotes/cli, then read from the published signed log:

export EPOCHNOTES_VERSIONS=https://mskrad.github.io/Epochnotes/registry/versions
curl -fsS https://mskrad.github.io/Epochnotes/registry/publishers.json -o epochnotes-publishers.json
export EPOCHNOTES_PUBLISHERS=./epochnotes-publishers.json
epochnotes registry read --json --status mainnet-beta   # verified entries and the state of each activation
epochnotes status --chain base                          # every activation the registry names on Base
epochnotes check repo <path>                            # where a change breaks this code
epochnotes check rpc --rpc-url <endpoint>               # does this provider behave as the entry says
epochnotes watch solana                                 # what moved on Solana since the last look

When it cannot verify what it reads, it refuses to answer rather than guess.
